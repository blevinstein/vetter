# vetter — Testing Plan

This document maps out the testing strategy for the `vetter` project. It is
organized by component and then by test category, with a section at the end
covering CI, tooling, and per-phase milestones that track the roadmap in
`Overview.md §11`.

---

## 1. Testing philosophy

The core security properties of `vet` are non-negotiable: a mistake in the
rule matcher, a parser that silently swallows a flag, or a render bug that
hides a header could mean an unauthorized request slips through. Tests here
serve two roles:

1. **Correctness guards** — catch regressions in matching, parsing, and
   rendering logic as the codebase grows.
2. **Documentation** — snapshot and fixture files record what the system
   decided about a real invocation, making policy auditable.

Test categories used throughout this document:

| Category | Description |
|---|---|
| **Unit** | Single function or type; no I/O |
| **Snapshot** | Golden-file diff of rendered or parsed output |
| **Property** | QuickCheck / proptest over algebraic invariants |
| **Integration** | Multiple components wired together; may use temp files / sockets |
| **E2E** | Full binary under a real shell; daemon running in tempdir |
| **Negative** | Asserts that a dangerous or malformed input is _rejected_ |

## 2. `vetter-core` — shared library

### 2.1 `Effect` / `ParsedCommand` types

**Unit tests**

- Serialize `ParsedCommand` to JSON and deserialize back; assert roundtrip
  equality for each `Effect` variant (`HttpRequest`, `FileWrite`, `FileRead`,
  `ProcessSpawn`, `CredentialUse`, `Network`).
- Assert that `ParsedCommand` JSON contains `"command"` and `"effects"` keys
  (wire protocol stability guard; add a forward-compat assertion if new fields
  are added with `#[serde(default)]`).
- `HttpRequest` field coverage: verify `method`, `url`, `headers`, `body`,
  `auth`, `tls`, `follow_redirects`, `proxy` all survive a roundtrip.
- `Body` variant coverage: `None`, `Inline`, `FromFile`, `Form`. (The
  former `FromStdin` variant was scrubbed when ThreatModel T9 closed —
  the curl parser now rejects every stdin-sourced body shape outright.
  A regression test pins that the old `"kind": "from_stdin"` JSON tag
  no longer deserialises.)
- `TlsPolicy` distinguishes `Strict` / `InsecureSkipVerify` / `Plaintext`.

**Negative**

- Deserializing a `ParsedCommand` with an unknown `"command"` value should
  succeed (forward-compat) and preserve the raw argv.
- Deserializing an unrecognized `Effect` variant should fail loudly, not
  silently drop the effect.

---

### 2.2 Parser registry

**Unit tests**

- `dispatch("curl")` returns the curl parser.
- `dispatch("/opt/homebrew/bin/curl")` returns the curl parser (basename
  matching).
- `dispatch("unknown-tool")` returns `None`.
- Registering two parsers claiming the same name should panic at startup
  (catches accidental duplicate registration).
- `all()` returns a non-empty list of parsers.

### 2.3 Renderer

The renderer turns a `ParsedCommand` into a styled text block. Its output is
the primary human-facing artifact, so correctness is critical.

**Snapshot tests** (`tests/snapshots/render/`)

Each fixture is a pair:
- `<name>.input.json` — a `ParsedCommand` (hand-written or generated by the
  curl parser test suite).
- `<name>.expected.txt` — the expected rendered output with ANSI stripped
  (plain text) and also with ANSI included (styled).

Fixture list (minimum):

| Fixture | Covers |
|---|---|
| `get_simple` | GET, no body, no auth, no signals |
| `post_json_bearer` | POST, JSON body, Authorization header redacted |
| `delete_with_api_key` | DELETE, X-Api-Key flagged |
| `insecure_tls` | `-k` badge, red TLS indicator |
| `file_write` | `-o /tmp/out`, `FileWrite` effect rendered |
| `file_read_upload` | `-d @path`, `FileRead` effect rendered |
| `multiple_effects` | Both HttpRequest + FileWrite in one command |
| `localhost_dev` | loopback URL, dim cyan coloring |
| `risk_signals_all` | All generic signals present simultaneously |
| `no_color_env` | `NO_COLOR=1` → plain text, no ANSI codes |
| `clicolor_force` | `CLICOLOR_FORCE=1` → ANSI even when not a TTY |
| `noop_parser` | Trivial parser; exercises the generic renderer path |

**Unit tests** (renderer internals)

- Header value redaction: a header named `Authorization` renders as
  `••••<last4>`, not the full value.
- Header value redaction: headers named `Cookie`, `X-Api-Key`,
  `X-*-Token`, `Proxy-Authorization` are also redacted.
- Header value not redacted: `Content-Type`, `Accept`, `User-Agent` are
  shown in full.
- Method coloring: `GET` → green class, `POST`/`PUT`/`PATCH` → yellow,
  `DELETE` → red, `CONNECT` → magenta.
- Match line: `"Match: matched rule <id>"` appears in green; `"Match: no
  rule"` in yellow; `"Match: denylist"` in red.
- `DisplayHints.badges` render as `[badge-text]` after the primary target.
- Long URLs are not truncated (full path must be visible for auditability).

### 2.4 Risk analyzer

**Unit tests** (pure function, no I/O)

For each signal kind, construct a minimal `ParsedCommand` that triggers it,
assert the expected `SignalKind` appears in the output; also construct a
variant that does not trigger it and assert it is absent.

| Signal | Triggers when |
|---|---|
| `WriteMethod` | method is POST / PUT / PATCH / DELETE |
| `AuthHeader` | headers contain Authorization / Cookie / X-Api-Key / etc. |
| `InsecureTls` | `tls == InsecureSkipVerify` or scheme is http and host is not loopback |
| `NonStandardPort` | port not in {80, 443, 8080, 8443} and not loopback |
| `IdnHost` | host contains xn-- punycode or non-ASCII chars |
| `RawIpLiteral` | host is a bare IPv4/IPv6 address (not `localhost` / `127.x` / `::1`) |
| `FileOutsideCwd` | `FileWrite.path` resolves outside the working directory |
| `FileReadOutsideCwd` | `FileRead.path` resolves outside the working directory |
| `PipeToShell` | `ProcessSpawn.command` contains `| sh`, `| bash`, `| zsh` patterns |

**Property tests** (proptest)

- `analyze(p)` is a pure function: same input always produces the same output.
- If `effects` is empty, the result is an empty `Vec<RiskSignal>`.
- Each signal in the result has an `effect_idx` that is a valid index into
  `p.effects`, or `None` for global signals.

### 2.5 Rule matcher

The matcher is the policy enforcement point. It has the highest density of
security-critical logic and warrants the most thorough testing.

**Unit tests** — one rule, one ParsedCommand

For each `when:` clause field, write tests verifying:

- **Method match / mismatch**: `method: [GET]` allows GET, rejects POST.
- **Scheme match**: `scheme: https` rejects `http://`.
- **Host exact match**: `host: api.github.com` rejects `api.github.com.evil.com`.
- **Host glob match**: `host: "*.github.com"` matches `api.github.com`.
- **Port match**: `port: [443]` rejects port 8080.
- **Path glob**: `path: "/repos/**"` matches `/repos/foo/bar` but not `/user`.
- **`no_body: true`**: rejects any request with a non-empty body.
- **`headers_allow`**: a request with `X-Extra-Header` absent from the list
  is rejected even if method/host/path match.
- **`headers_allow: ["*"]`**: wildcard suppresses header restriction.
- **`command:` filter**: a rule with `command: curl` matches a curl
  `ParsedCommand` but not one from a `noop` parser.
- **Multiple effects**: a rule with both `http:` and `file_write:` clauses
  requires both effects to be present; omitting either causes a miss.
- **`file_write:` clause**: path glob matching for output files.

**Property tests** (proptest)

- A rule that exactly matches a generated `ParsedCommand` always returns true.
- Mutating any single matched field of the command (method, host, path, a
  header, body presence) produces a non-match (fuzz the mutation type).
- `matches(p, rule)` never panics on any valid `ParsedCommand`.

**Negative / security tests**

- A rule allowing `GET api.github.com` does not match
  `GET api.github.com.attacker.com` (host suffix confusion).
- A rule allowing `path: /admin` does not match `path: /admin/../secret`
  (path traversal; the URL should be normalised before matching).
- A rule with `headers_allow: [Authorization]` does not silently allow an
  additional `X-Secret` header that was not listed.
- An empty `headers_allow: []` blocks all requests (default-deny semantics).
- A later allowlist layer overriding an earlier one is tested: session-scope
  allow overrides user-scope deny; denylist overrides all allows at every layer.
- Denylist entry for a specific host blocks even a rule that would otherwise
  allow it.

---

### 2.6 Allowlist loader

**Unit tests**

- Valid YAML with one rule loads without error; `id`, `when`, `note` are
  populated.
- YAML with duplicate `id` values returns an error.
- Unknown top-level fields are rejected (strict schema: unknown keys should
  not silently be ignored, to surface typos in user-edited files).
- `note`, `created_by`, `created_at` are optional.
- Empty `rules: []` loads without error.

**Integration tests**

- Walk from a nested directory up to a `<repo>/.vet/allowlist.yaml`; the
  project-scope rules are merged.
- User-scope file at `~/.vet/allowlist.yaml` is merged at lower
  precedence.
- Atomic write: simulate a crash mid-write (replace temp file process);
  the allowlist on disk is either the old file or the new file, never
  a partial write.
- `vet allow add` appends a rule and the file remains valid YAML.
- `vet allow rm <id>` removes exactly the rule with that id.

## 3. `curl` parser

The curl parser is the most complex single component and is the only source
of `ParsedCommand` instances for MVP. It directly affects policy correctness.

### 3.1 Flag corpus snapshot tests

Maintain a directory `tests/corpus/curl/` of fixture files. Each fixture:

```
tests/corpus/curl/<name>.argv    # one flag/arg per line
tests/corpus/curl/<name>.json    # expected ParsedCommand (serde JSON)
```

Fixtures should cover real invocations harvested from agent transcripts plus
hand-crafted edge cases. Minimum fixture set:

| Fixture | Covers |
|---|---|
| `simple_get` | `curl https://example.com` |
| `post_json_data` | `-X POST -H Content-Type:application/json -d '{"k":"v"}'` |
| `post_form` | `--data-urlencode key=val --data-urlencode other=val2` |
| `bearer_auth` | `-H 'Authorization: Bearer tok'` |
| `basic_auth_flag` | `--user alice:secret` |
| `netrc_auth` | `--netrc` |
| `insecure` | `-k` (InsecureSkipVerify TLS) |
| `output_file` | `-o /tmp/out.json` (FileWrite) |
| `output_auto` | `-O` (FileWrite, basename from URL) |
| `upload_file` | `-T /path/to/file` (FileRead) |
| `upload_stdin` | `-T -` → ParseError::StreamingUnsupported |
| `data_at_file` | `-d @./payload.json` (FileRead) |
| `data_at_stdin` | `-d @-` → ParseError::StreamingUnsupported if >1 MiB |
| `follow_redirect` | `-L` |
| `proxy` | `--proxy http://proxy.corp:8080` |
| `resolve_override` | `--resolve api.example.com:443:1.2.3.4` → RiskSignal |
| `cacert_override` | `--cacert /etc/custom.pem` → RiskSignal |
| `unix_socket` | `--unix-socket /var/run/docker.sock` → RiskSignal |
| `multiple_headers` | Multiple `-H` flags; order preserved |
| `verbose_flags` | `--verbose --silent --fail` (extras, no effect changes) |
| `implicit_get` | No `-X`; method defaults to GET |
| `implicit_post` | `-d` present and no `-X`; method defaults to POST |
| `chunked_transfer` | `--header Transfer-Encoding:chunked` → StreamingUnsupported |
| `url_with_query` | URL with `?key=val&key2=val2` |
| `url_with_fragment` | Fragment stripped before request |
| `argv0_variants` | `/usr/bin/curl`, `/opt/homebrew/bin/curl`, `curl3` |

**Negative fixtures** (parser must return `Err`)

| Fixture | Reason |
|---|---|
| `no_url` | No URL provided |
| `conflicting_methods` | `-X GET` and `-X POST` both present |
| `unknown_flag` | `--unknown-future-flag` (unknown flags surface in `extras`, not error — document the chosen behavior) |

### 3.2 Unit tests (curl-specific signals)

- `--insecure` / `-k` produces `SignalKind::InsecureTls` in `signals`.
- `--resolve` produces `SignalKind::ResolveOverride` (or equivalent) in `signals`.
- `--cacert` produces `SignalKind::CacertOverride` in `signals`.
- `--unix-socket` produces a signal.
- `--insecure` sets `tls == InsecureSkipVerify` on the `HttpRequest` effect.
- `http://` URL for a non-loopback host → `InsecureTls` signal from generic analyzer.
- `http://localhost` → no `InsecureTls` signal (loopback carve-out).

### 3.3 Body handling

- `-d 'literal'` → `Body::Inline`, size ≤ 1 MiB.
- `-d @file` → `Body::FromFile`, `FileRead` effect emitted.
- `-d @-` (and `--data @-`, `--data-binary @-`, `--data-ascii @-`,
  `--data-urlencode @-`) → `ParseError::StreamingUnsupported`,
  independent of stdin contents (ThreatModel T9 close). Sister to
  the existing `-T -` / `-b @-` / `-w @-` / `-K -` rejections;
  agents must materialise the body to a temp file and use
  `-d @file`. `--data-raw @-` is *not* rejected because curl
  treats `@` as a literal byte under `--data-raw`.
- Multiple `-d` flags → values concatenated per curl behavior.
- `--data-urlencode` values → `Body::Form` with url-encoded fields.
- Content-Type automatically inferred as `application/x-www-form-urlencoded`
  when `--data-urlencode` is used and no explicit Content-Type given.

## 4. `vet` CLI binary

### 4.1 Exit codes

Integration tests that spawn the `vet` binary:

| Scenario | Expected exit code |
|---|---|
| Daemon running, rule allows request | 0 (+ exec'd command also exits 0) |
| Daemon running, rule denies request | 77 |
| Daemon running, config file malformed | 78 |
| Daemon not running | non-zero with "daemon not running" message |
| Daemon running, wrapped command exits 1 | 1 (passthrough) |
| Daemon running, wrapped command exits 2 | 2 (passthrough) |

### 4.2 `--explain` mode

- Does not exec the underlying command (check no side effects via mock command).
- Prints the renderer output to stderr.
- Prints the policy decision (allow/deny/prompt) to stderr.
- Exits 0 even if the decision would be "deny" (explain is read-only).

### 4.3 `--dry-run` mode

- Always routes to the "prompt" path, never auto-allows, even if a matching
  rule exists.
- Does not exec the underlying command.

### 4.4 Output routing

- In normal mode, renderer output goes to **stderr**, not stdout.
- Wrapped command's stdout passes through unmodified (integration test:
  `vet curl` against a local HTTP server; assert stdout is the response body,
  not intermixed with render output).
- `--quiet` suppresses the render on stderr; the wrapped command still runs.

### 4.5 Color detection

- When stderr is not a TTY (`vet ... 2>/tmp/err`), ANSI codes are absent
  in `/tmp/err` unless `CLICOLOR_FORCE=1`.
- `NO_COLOR=1` suppresses ANSI even when stderr is a TTY.
- `CLICOLOR_FORCE=1` forces ANSI even when stderr is not a TTY.

### 4.6 `vet allow` subcommands

- `vet allow add 'when: {http: {method: [GET], url: {host: example.com}}}'`
  appends a rule to the user-scope file.
- `vet allow rm <id>` removes the rule with that id; errors clearly if id not
  found.
- `vet allow list` prints loaded rules from all scopes with their scope label.
- `vet allow list --scope project` prints only project-scope rules.
- `vet allow list --history` prints the last N lines of the audit log.

### 4.7 `vet doctor`

Each check yields one of `OK` / `WARN` / `ERROR` / `INFO` / `SKIP`.
`vet doctor` exits `78` if any check is `ERROR`, else `0`. `WARN`
does not change the exit code (so the developer's daily `vet doctor`
stays exit-0 if the daemon is healthy but, say, the audit dir has
slightly loose perms).

Required rows, in order:

- **daemon** — walks pidfile → live-PID → socket → peer-cred:
  - both pidfile + socket absent → `INFO not running`.
  - socket present without pidfile → `ERROR orphan socket`.
  - pidfile parses but PID is dead (`kill(pid, 0) == ESRCH`) →
    `ERROR stale pidfile`.
  - pidfile + live PID but socket unreachable →
    `ERROR pidfile points at live pid but socket is unreachable`.
  - all of the above plus peer-cred mismatch on `connect()` →
    `ERROR socket peer uid=<N>, expected uid=<M>`.
  - all checks pass → `OK pid=<N>, uptime=<…>, peer_uid=<N>`.
- **socket** — `metadata.mode() & 0o777 == 0o600` and owner is the
  current uid; mode mismatch is `WARN`, foreign owner is `ERROR`.
  `SKIP` if absent.
- **socket parent dir** — same shape, expected mode `0o700`.
  Foreign owner is `ERROR` (the parent dir is the cross-user
  containment boundary). `INFO` if absent (will be created on next
  `vet daemon start`).
- **pidfile** — `OK present` / `INFO absent`; the substantive errors
  are already raised by the daemon row.
- **audit log** — `OpenOptions::append + create` succeeds → `OK`,
  else `ERROR <os error>`.  `vet doctor` does **not** create parent
  directories — that's the daemon's job; missing parents should
  surface as a clear error.
- **allowlist (user)** — `SKIP` if absent, `OK <N rules, M deny>` if
  parses, `ERROR` with path + parse error otherwise.
- **allowlist (project)** — `SKIP` if no `.vet/allowlist.yaml` is
  found walking up from cwd; otherwise same shape as user.
- **allowlist (override)** — only printed when `--allowlist <path>`
  was given. Same shape as user.
- **parsers registered** — `OK <count> (<names>)`. An empty registry
  is `ERROR` (binary likely misbuilt).
- **code signing (vet)** / **code signing (vetterd)** — on macOS,
  shells out to `codesign --verify --strict` then `codesign -d -vv`
  on each binary. `OK` for Developer-ID Application authority +
  `--options runtime` (hardened runtime); `WARN` for ad-hoc signed
  (`Signature=adhoc`, the cargo + `codesign --sign -` dev path) or
  Developer-ID without the hardened runtime; `ERROR` if `codesign
  --verify` fails or the binary path cannot be resolved. The
  `vetterd` binary is resolved via the same logic `vet daemon start`
  uses (`$VETTERD_BIN` → sibling-of-`vet` → `PATH`). Off macOS the
  whole block collapses to a single `code signing SKIP macOS only`
  row — distribution is macOS-only, so a signature on Linux is
  meaningless.
- **code signing (bundle)** — emitted only when both binaries
  resolve to the same `<Name>.app/Contents/MacOS/`. Runs `xcrun
  stapler validate` then `spctl --assess --type execute --verbose=4`
  on the bundle. `OK` only when both succeed (notarised + stapled +
  Gatekeeper-accepted, the artifact `tools/release.sh` produces);
  `WARN` for ad-hoc bundles or Developer-ID bundles missing the
  staple; `ERROR` if `codesign --verify` against the bundle fails.

Test matrix lives in [`vet/tests/doctor.rs`](../vet/tests/doctor.rs):
clean state, real running daemon, stale pidfile, orphan socket,
loose parent perms, malformed allowlist override, unwritable audit
dir.

### 4.8 `vet daemon start/stop/status`

- `start` when daemon already running prints a warning but exits 0.
- `stop` sends SIGTERM and waits for the socket to disappear.
- `status` reports uptime and pending-request count.

### 4.9 Fail-closed behavior (critical security test)

- Remove the socket file; `vet curl https://example.com` exits non-zero
  with the message "daemon not running, run `vet daemon start`".
- No interactive TTY prompt is shown; stderr contains only the error message,
  not any "Do you want to allow? [y/N]" text.
- `vet curl …` does not exec the underlying `curl` binary in any
  fail-closed path (verify by substituting a mock that writes a sentinel
  file; assert the file does not exist after the test).

## 5. `vetterd` daemon

### 5.1 Socket lifecycle

- Daemon creates the socket at startup.
- Daemon removes the socket on clean exit.
- Daemon removes a stale socket file left by a previous crash and recreates it.
- Two concurrent `vet` clients get independent decisions (no request
  cross-contamination).

### 5.2 Request queue

- Multiple requests can be pending simultaneously; each blocks independently.
- Decision for request A does not unblock request B.
- A denied decision is returned to the right client even when requests arrive
  out of order.

### 5.3 Allowlist persistence (atomic writes)

- Approving with "Allowlist" adds the rule to the correct scope file.
- The file is a valid YAML after the write (parse it and assert no error).
- Simulate SIGKILL between the temp-file write and the rename; the old file is
  intact (test the rename-based atomic write directly, not the whole daemon).

### 5.4 Audit log

- Every decision (auto-allow, auto-deny, human-allow, human-deny) produces one
  JSON-lines entry.
- Each entry includes: `id` (ULID), `timestamp`, `command`, `argv`,
  `decision`, `reason`, `rule_id` (nullable).
- Log entries are flushed before the decision is returned to `vet` (so a
  crash after the decision doesn't lose the log entry).
- `vet allow list --history` shows the last N entries in chronological order.

### 5.5 Session-scope decisions

- `allow_once` decisions are stored in-memory only.
- After daemon restart, a previously `allow_once`-allowed request is routed
  to the prompt path again (not auto-allowed).

## 6. Wire protocol

### 6.1 Serialization

- Round-trip `VetRequest` → JSON → `VetRequest`; assert all fields preserved.
- Round-trip `VetDecision` → JSON → `VetDecision`.
- Length-prefix framing: a message with length N is framed as a 4-byte
  big-endian prefix followed by N bytes; assert decode(encode(msg)) == msg.
- Empty body (zero-length message) is handled without panic.

### 6.2 Version negotiation

- A `VetRequest` with `"v": 1` is accepted by a daemon expecting v1.
- A `VetRequest` with `"v": 99` is rejected with a clear version-mismatch
  error (daemon does not panic or hang).
- Daemon sends `"v"` field in `VetDecision`; client checks it.

### 6.3 Protocol fuzzing

- Feed random bytes of varying lengths to the daemon's socket reader;
  assert no panic and a well-formed error response (or connection close)
  is returned within 1 second.

## 7. Security properties (cross-cutting)

These tests assert invariants that span multiple components and must not
regress regardless of refactors.

| Property | Test approach |
|---|---|
| Agent cannot self-approve | The `vet` binary has no code path that prompts on its own TTY; static + integration test. |
| Fail-closed if daemon missing | §4.9 above. |
| Header default-deny | Rule with no `headers_allow` and no `*` never auto-allows any request with extra headers. |
| Denylist beats all | A denylist entry for a host blocks the request even when a higher-precedence allow rule would permit it; test all 5 allowlist layers. |
| No partial-write allowlist | §5.3 above. |
| Redacted secrets never appear in stdout | Rendered output on stdout (with `--quiet` off) never contains the raw value of an Authorization or Cookie header; use a known bearer token in a fixture and assert it doesn't appear in unredacted form. |
| `execvp` only on allow | The wrapped binary is executed only after a final `decision: allow` from the daemon; on `deny` or `allow_once` + deny, no exec occurs. |

## 8. Additional parsers (Phase 7+)

Each new parser added in Phase 7 must include:

1. A fixture corpus in `tests/corpus/<name>/` covering at minimum:
   - A simple "happy path" invocation.
   - An invocation with credentials/auth.
   - An invocation with a write/destructive effect.
   - At least two error cases.
2. All unit tests from §2.2 (registry), §3.2 (signal coverage) adapted to
   the new command.
3. A round-trip snapshot test confirming the renderer handles its effects
   without curl-specific branching.
4. A matcher test confirming a generic `http:` rule (no `command:` filter)
   matches the new parser's `HttpRequest` effects.

Adding `wget` first is a useful integration check: if the `wget` parser
forces changes to `Effect`/`ParsedCommand`, fix them before adding more
parsers.

### 9.2 Test organization

```

vetter-core/tests/       ← integration tests for core
  render/
    snapshots/           ← insta snapshot files

tests/e2e/               ← workspace-level E2E tests

```

### 9.3 Fixture update workflow

When a snapshot needs updating:
1. Run `UPDATE_EXPECT=1 cargo test` (or `cargo insta review`).
2. Review the diff; confirm the change is intentional.
3. Commit the updated snapshot alongside the code change.

Snapshots should never be updated silently by CI — they require a human
review step.

### 9.4 Corpus management

The curl corpus lives in version control. When a new real-world invocation
surfaces a bug:
1. Add the argv as a new `<name>.argv` fixture.
2. Add the expected `ParsedCommand` as `<name>.json`.
3. Run tests; fix the parser.
4. Commit both the fixture and the fix.

This creates a regression test for every parser bug.

## 10. CI strategy

```yaml
# Conceptual CI job structure
jobs:
  fmt:       cargo fmt --check
  clippy:    cargo clippy -- -D warnings
  test:
    matrix: [macos-latest, ubuntu-latest]
    steps:
      - cargo nextest run --workspace
      - cargo llvm-cov --workspace --lcov --output-path lcov.info
      - (fail if core coverage < 80%)
  snapshots: cargo insta test --unreferenced=error  # fail on unreviewed diffs
  e2e:
    runs-on: macos-latest        # daemon UI only ships on macOS
    steps: cargo nextest run --test e2e
```

Ubuntu runner is used for headless tests of `vetter-core`, `vet` (without
exec), and `vetterd` — through Phase 5 the GTK / D-Bus side is gated
behind `cfg(target_os = "linux")` and a `MockNotifier`-style mock D-Bus
server, so neither a graphical session nor a real notification daemon
is required. From Phase 6 onward the Ubuntu test job additionally runs
`apt-get install -y libgtk-4-dev libdbus-1-dev` so the linux notifier
+ tray + popover code compiles, and a separate `deb` job runs
`cargo install cargo-deb && cargo deb -p vetterd --no-build` to produce
the package artifact and asserts its `dpkg-deb --contents` matches an
expected manifest. macOS runner remains required for the full E2E suite
and for testing `UNUserNotificationCenter` integration (Phase 4+).

## 12. Known gaps and future work

- **macOS UI automation tests**: `UNUserNotificationCenter` actions are hard
  to drive headlessly. For MVP, test the daemon's decision-routing logic with
  a stub UI; defer UI automation to post-MVP.
- **Concurrency stress tests**: The daemon's request queue under high
  concurrency (100+ simultaneous `vet` clients) is not tested in MVP.
  Add a stress harness in Phase 5.
- **Corpus growth**: The curl corpus starts small. Establish a process for
  continuously feeding new invocations from agent transcripts into the fixture
  set post-MVP.
- **Protocol fuzzing**: §6.3 outlines fuzzing; consider adding `cargo-fuzz`
  targets for the socket framing and YAML loader in a post-MVP hardening pass.
- **GTK runtime tests**: Phase 6 lands the GTK4 popover; assertions
  that exercise `gtk::Box::append`, `pango::AttrList`, and
  `StatusNotifierItem` registration require an X / Wayland session and
  a tray host on the bus. CI runs the *non-GTK* half (queue → card-data
  lowering, `ResolvePending` admin round-trip, mock-D-Bus `ActionInvoked`
  routing) headlessly; the popover-widget side stays manual via
  [`plans/UbuntuApp.md`](UbuntuApp.md) §"Manual smoke test" until we
  invest in a `Xvfb` + `dbus-run-session` harness.
- **Windows tests**: Not needed until Phase 8; ensure the core library
  unit tests (no UI, no Unix sockets) compile and pass on Windows CI
  from Phase 1 onward to avoid a large cross-platform debt later.
